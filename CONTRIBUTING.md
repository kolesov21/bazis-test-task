# Соглашения по работе с проектом

Запуск и основное поведение описаны в [README.md](./README.md), устройство приложения и инварианты — в [AGENTS.md](./AGENTS.md).

## Язык и документация

Общение, документация проекта, описания изменений и сообщения коммитов — на русском языке. Идентификаторы в коде, имена веток, технические префиксы коммитов и имена инструментов — на английском. Сторонние скиллы и лицензии сохраняют язык оригинала.

Комментарии пишите по-русски и оставляйте только для неочевидных причин, ограничений и защиты от ошибок. Не пересказывайте код. README сохраняйте кратким: запуск, проверки, структура и существенное поведение; подробности реализации проверяйте по коду и тестам.

## Ветки

Основная ветка — `main`; включайте в неё изменения после проверок и ревью. Задача с изменением файлов выполняется в отдельной короткоживущей ветке от актуальной `main`; если для задачи уже есть рабочая ветка, работа продолжается в ней. Для анализа без правок отдельная ветка не нужна.

Формат: `<тип>/<краткое-описание>`. Используйте строчную латиницу, цифры и дефисы; слова описания — на английском, без транслитерации русского текста. Одна ветка соответствует одной связанной задаче. Если есть номер задачи, его можно добавить перед описанием: `fix/42-draft-recovery`.

| Тип        | Назначение                             | Пример                      |
| ---------- | -------------------------------------- | --------------------------- |
| `feat`     | Новая функциональность                 | `feat/note-search`          |
| `fix`      | Исправление ошибки                     | `fix/draft-recovery`        |
| `refactor` | Переработка без изменения поведения    | `refactor/note-history`     |
| `docs`     | Документация и правила проекта         | `docs/project-conventions`  |
| `test`     | Тесты и их инфраструктура              | `test/storage-conflicts`    |
| `chore`    | Зависимости, конфигурация, инструменты | `chore/update-dependencies` |

Отдельные постоянные `develop`, `release` и `hotfix`-ветки для этого проекта не нужны. Не создавайте ветки с именами `temp`, `changes` или `final`.

В рамках разрешённой задачи можно создавать локальные ветки и коммиты. После проверки и ревью локальную ветку можно включить в `main` через `git merge --ff-only <ветка>`. Если fast-forward невозможен, сначала изучите расхождение; не переписывайте общую историю автоматически. Удаляйте рабочую ветку только после включения её изменений и проверки отсутствия уникальных коммитов.

Push выполняется только по явному поручению пользователя. Локальный коммит или merge не означает разрешения на push.

Перед публикацией выполните `git fetch origin` и проверьте расхождение с целевой удалённой веткой. После push убедитесь, что отправлен нужный коммит, и проверьте состояние рабочего дерева.

## Коммиты

Формат заголовка:

```text
<тип>[(область)]: <действие и результат на русском>
```

Типы совпадают с таблицей веток. Область необязательна: добавляйте её, когда она помогает понять затронутую часть (`notes`, `history`, `storage`, `ui`, `tests`, `git`). Для отдельного улучшения производительности допустим `perf`, для CI — `ci`. Они также могут использоваться как тип ветки.

Описание начинается со строчной буквы и глагола в неопределённой форме: «добавить», «исправить», «обновить», «удалить». В конце заголовка нет точки. Ориентир длины — до 72 символов, без потери смысла. Названия API, пакетов и идентификаторы можно оставлять на английском.

```text
feat(notes): добавить поиск по названиям заметок
fix(storage): предотвратить восстановление удалённой заметки
test(history): проверить очистку ветки повторных изменений
docs(git): закрепить правила веток и русских сообщений коммитов
chore: обновить зависимости проекта
```

Один коммит — одно законченное логическое изменение. Исправление ошибки поведения включает относящийся к нему регрессионный тест; не отделяйте тест искусственно ради количества коммитов. Для правок документации и обычных комментариев новые тесты не нужны. Не смешивайте функциональность с несвязанным форматированием. Перед коммитом просмотрите staged diff и включите только файлы текущей задачи, сохраняя чужие изменения вне коммита.

Для сложного изменения после пустой строки добавьте тело на русском: причина, изменение поведения, существенные ограничения и выполненные проверки. Не заявляйте о проверках, которые не запускались. Избегайте сообщений «правки», «обновление», `WIP` и `fix stuff`.

Для несовместимого изменения используйте `!` после типа/области и пояснение `BREAKING CHANGE:` с русским текстом. Не используйте этот маркер для обычного исправления ошибки.

Менять сообщения уже созданных коммитов, делать amend/rebase или иным способом переписывать историю можно только по явному поручению пользователя. Перед этим проверьте, опубликована ли история. Force-push требует отдельного явного указания. При переводе сообщений сохраняйте авторство и даты. Не меняйте Git-идентичность без указания пользователя, в том числе при предупреждении Git об автоматически выбранном имени или email.

## Проверки и сдача

- Для всех изменений: `git diff --check`, `npm run format:check` и отдельный проход ревью итогового diff по [AGENTS.md](./AGENTS.md#проверки-и-обязательное-ревью).
- Для документации и обычных комментариев: проверьте смысл, ссылки, согласованность с кодом и отсутствие изменений логики. Сборка и тесты приложения не нужны. Директивы TypeScript, Vite и других инструментов не считайте обычными комментариями: их изменение может влиять на сборку или поведение.
- Для кода, зависимостей и конфигурации приложения: `npm run check` — типы приложения и тестов, unit-тесты и production-сборка. Тесты должны проверять поведение, ошибки и существенные граничные случаи.
- Для интерфейса, маршрутизации и браузерного хранения: дополнительно запускайте относящиеся к изменению Playwright-сценарии. При изменении внешнего вида просмотрите desktop/mobile-скриншоты после завершения анимаций.
- Для Dockerfile и Compose: проверьте сборку образа и запуск приложения, если Docker доступен; иначе укажите, что запуск не проверен.

Playwright запускает production-сервер на порту 3001. Нужна сборка текущего кода: успешный `npm run check` уже включает её; повторный `npm run build` нужен только после новых изменений, влияющих на сборку. Проекты — `chromium`, `firefox`, `webkit` и `mobile` (эмуляция iPhone 13 в WebKit). При изменениях общего браузерного поведения проверяйте все проекты; для отдельных сценариев используйте `--project` и `--grep`.

Исправьте замечания ревью и повторите затронутые проверки. В результате работы укажите изменения, реальные проверки, текущую ветку/коммит, факт публикации и существенные ограничения. Старый отчёт, успешная проверка другой версии, сбой запуска браузера или недоступный инструмент не подтверждают текущую работоспособность.

Соглашение закреплено документацией; автоматические Git-хуки и commitlint не устанавливаются без отдельной необходимости.
