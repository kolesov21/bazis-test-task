# Инструкции для работы в репозитории

Эти правила действуют для всего проекта. Явные указания пользователя имеют приоритет над локальными соглашениями. Общайтесь и документируйте результат на русском языке.

## Сначала прочитайте

- [CONTRIBUTING.md](./CONTRIBUTING.md) — обязательные правила веток, коммитов, проверок и публикации.
- [README.md](./README.md) — запуск, структура, поведение и принятые решения.
- [ТЗ.pdf](./ТЗ.pdf) — исходные требования; при изменениях учитывайте последующие уточнения пользователя.

Перед изменениями изучите `git status`, текущую ветку, последние коммиты и затронутые файлы. Не удаляйте и не включайте в свой коммит чужие изменения. Для поиска используйте `rg`.

## Обязательные скиллы

При первом применении скилла в разговоре сообщите об этом пользователю и прочитайте его инструкции. Используйте локальные версии:

1. [grill-me](./skills/grill-me/SKILL.md) — перед новой задачей и при существенном изменении требований. Сначала ищите ответы в материалах и переписке; уточняйте только существенные пробелы. Обычные детали реализации выбирайте самостоятельно. Если скилл требует остановки, сошлитесь на конкретное правило.
2. [ponytail](./skills/ponytail/SKILL.md) — для кода, зависимостей, рефакторинга и ревью; режим по умолчанию `full`. Реализуйте минимальное полное решение, переиспользуйте существующее, не добавляйте абстракции и зависимости «на будущее».
3. [frontend-design](./skills/frontend-design/SKILL.md) — при создании или изменении интерфейса. Согласованный ориентир — Notion: спокойная светлая палитра, типографика редактора документов, простые списки и минимум декора. Сначала краткий план, затем сверка с задачей, реализация и визуальная проверка.

Если обязательный скилл отсутствует, сначала найдите его в проекте; если найти не удалось, сообщите об этом, не имитируя применение.

## Устройство проекта и границы изменений

Приложение — SPA на Nuxt 4, Vue Composition API и TypeScript strict; состояние — Pinia, стили — собственный SCSS. Используйте npm и сохраняйте `package-lock.json`. Версии и команды берите из `package.json`, а не из памяти. Не обновляйте зависимости в несвязанной задаче.

- `app/domain/` — модель, валидация, история и операции хранения; без зависимости от Nuxt-компонентов.
- `app/stores/` — сохранённые заметки, операции сохранения/удаления, синхронизация и ошибки.
- `app/composables/` — сессия редактора и взаимодействие с интерфейсом.
- `app/components/` — переиспользуемые части UI; `app/pages/` — страницы списка и редактора.
- `tests/unit/` — история, стор, формат хранения; `tests/e2e/` — пользовательские сценарии в браузере.

Не добавляйте UI-библиотеки, библиотеки undo/redo или плагины автоматического persistence: это запрещено ТЗ. Не ослабляйте strict-типизацию ради прохождения проверки.

## Инварианты приложения

- История содержит обратимые операции, а не 50 полных копий заметки. Непрерывный ввод группируется; действия с задачами атомарны; новая правка очищает redo. Лимит — 50 шагов, границы сессии сбрасывают историю.
- Редактирование не меняет сохранённую заметку до успешного сохранения. Ошибка записи не должна терять рабочий текст или сообщать об успехе.
- Сохранённые данные имеют версию схемы. Неизвестные/повреждённые данные нельзя молча перезаписывать. Изменение схемы требует явного решения о совместимости.
- Черновики изолированы по вкладкам и переживают перезагрузку. Ожидание сохранения не должно препятствовать записи черновика при закрытии страницы.
- Перед записью сверяется ревизия; сохраняются межвкладочные блокировки и приоритет постоянного маркера удаления. Устаревшая вкладка не должна восстанавливать удалённую заметку.
- Подтверждения выполняются собственным модальным компонентом, без alert/confirm. Сохраняйте focus-trap, Escape, возврат фокуса, подписи, видимый фокус и клавиатурные сценарии.
- Ctrl/⌘ Z и Shift Ctrl/⌘ Z не должны вызывать одновременно историю приложения и нативную отмену поля.
- При смене идентификатора заметки создаётся новая сессия редактора. Не обходите подтверждение несохранённых изменений при переходе между редакторами; переход внутри той же страницы не сбрасывает сессию.

## Проверки и обязательное ревью

Подбирайте проверки по изменению согласно [CONTRIBUTING.md](./CONTRIBUTING.md). `npm run check` проверяет типы приложения и тестов, unit-тесты и production-сборку. Playwright запускает production-сервер на порту 3001, поэтому перед ним нужна свежая сборка. Форматирование — `npm run format:check`.

После реализации выполните отдельный проход ревью итогового diff:

1. Сопоставьте поведение с запросом и применимыми пунктами ТЗ; проверьте все изменённые вызовы и граничные случаи.
2. Проверьте целостность данных, обработку ошибок, асинхронные гонки, черновики, ревизии и удаление в другой вкладке, если они затронуты.
3. Проверьте типы и валидацию внешних данных, безопасный вывод текста, отсутствие секретов и ненужных зависимостей.
4. Для UI проверьте клавиатуру, фокус, состояния загрузки/ошибки/пустого списка и мобильную вёрстку.
5. Убедитесь, что тесты проверяют поведение и регрессии, а не повторяют реализацию; документация и конфигурация соответствуют коду.
6. Исправьте замечания до сдачи и повторите необходимые проверки. Не называйте собственное ревью независимым ревью другим агентом.

Постоянный дополнительный скилл ревью не нужен: этот список — обязательный минимум. При изменении только документации проверьте сами правила, ссылки и отсутствие противоречий; тесты приложения для этого не требуются.

## Git и завершение работы

Следуйте [CONTRIBUTING.md](./CONTRIBUTING.md): рабочие ветки `<тип>/<english-kebab-case>`, заголовки коммитов `<тип>[(область)]: <описание на русском>`. Перед коммитом просмотрите staged diff. Сохраняйте лицензии и атрибуцию в `skills/`.

Для разрешённой задачи можно создавать локальные ветки и коммиты; после проверок и ревью допустим локальный fast-forward в `main`. Не выполняйте push без явного поручения пользователя. Не переписывайте историю, не меняйте Git-идентичность и не используйте force-push без соответствующего явного указания.

Не считайте старый отчёт, успешную проверку другой версии или недоступный браузер текущей верификацией. В итоговом сообщении кратко перечислите результат, реальные проверки и непроверенные части. Не создавайте дополнительные AGENTS.md в подкаталогах, пока для них не нужны отличающиеся правила.
